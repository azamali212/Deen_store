NOTE (Auth domain, 2026-09-21): captcha_token temporarily removed
──────────────────────────────────────────────────────────────────
Postman/API testing was blocked by `captcha_token` being hardcoded
`required` on LoginRequest, CreateUserRequest, ForgotPasswordRequest,
ResetPasswordRequest — even though .env has CAPTCHA_ENABLED=false.
That config flag was never actually read anywhere (dead config).

Removed for now, until the frontend (which will run the real
Cloudflare Turnstile widget) is built:
  - captcha_token rule dropped from all 4 FormRequests above.
  - captchaToken property + fromArray() mapping dropped from
    LoginDTO, CreateUserDTO, ResetPasswordDTO, ForgotPasswordDTO.
  - AuthService::login() no longer calls CaptchaService->verify();
    CaptchaService injection + unused imports (VerifyCaptchaDTO,
    CaptchaService) removed from AuthService.

NOT deleted — kept intact for later: the whole Domain/Captcha module
(CaptchaService, CaptchaProviderInterface, CloudflareTurnstileProvider,
VerifyCaptchaDTO, InvalidCaptchaException, VerifyCaptchaAction) and the
turnstile config/.env keys. When frontend sends real Turnstile tokens,
re-add `captcha_token` to the 4 FormRequests + DTOs and re-wire the
verify() call in AuthService::login() (and add it to createUser/
forgotPassword/resetPassword flows too if desired — those never called
CaptchaService at all, even before this change).

Above Postman collection note ("login requires captcha_token, so that
one step still has to be done manually") is now stale — login no longer
needs captcha_token.

──────────────────────────────────────────────────────────────────
NOTE (Auth domain, 2026-09-21): customer self-registration fixed
──────────────────────────────────────────────────────────────────
Found: CustomerAuthController::canRegister() was false, AND
routes/auth/customer.php had /register sitting INSIDE the
auth:sanctum+role:customer middleware group — a brand-new visitor
with no token could never reach it. Self-registration was completely
broken/disabled, admin was the only way any account got created.

Fixed with a NEW, separate path (did not touch the existing admin-only
register()/CreateUserRequest flow):
  - app/Http/Requests/Auth/RegisterCustomerRequest.php — public, no
    `role` field at all (name/email/password/phone only).
  - CreateUserDTO::forSelfRegistration() — new factory, role is a
    hardcoded PHP argument the caller controls, never read from
    request input. This is the actual security fix: a public endpoint
    must never let the caller pick their own role.
  - BaseAuthController::registerSelf() — new method + new abstract
    selfRegistrationRole(): ?SystemRole (mirrors the existing
    canRegister() pattern). Returns SystemRole::CUSTOMER for
    CustomerAuthController, null (403) for Admin/Seller.
  - routes/auth/customer.php — /register moved OUT of the auth
    middleware group, points to registerSelf instead of register.

Already worked without any change, confirmed by reading the code:
  - UserCreated event already fires SendWelcomeEmailListener +
    RequestEmailVerificationListener + ProvisionDefaultPreferencesListener
    — a self-registered customer gets a welcome email, an email
    verification request, and default preferences automatically.
  - ProfileService::updateProfile() already does create-or-update
    (upsert) — no separate "create profile" endpoint was ever needed,
    the same PUT /profile endpoint creates the row on first call.

NOT done (out of scope, noted only): SellerAuthController's
self-registration is deliberately still null/disabled — Stage B
(customer-initiated seller upgrade request -> admin approval -> bank
details) is deferred per earlier decision. routes/auth/customer.php
is also still missing verify-email/resend-verification/forgot-password/
reset-password routes that admin.php has — not touched, flagging for
later.
