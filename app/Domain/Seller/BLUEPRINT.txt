0. DECISIONS
--------------------------------------------------------------------------------
Carried over from v1:
  D1. 5 required documents: cnic_front, cnic_back, business_license,
      tax_certificate, bank_statement.
  D2. Rejection flow: the user edits the SAME application row and resubmits
      (rejected -> pending). Never a new row.

Decided in the v1 review:
  D3. Bank account: the FULL number is stored, encrypted with Laravel's
      `encrypted` cast. (Payouts need the full number — storing only the
      last 4 digits would make paying a seller impossible.) A separate
      bank_account_last4 column is kept for display. The full number is
      NEVER returned by any API; responses only show "****1234".
  D4. Tamper-evident (hash-chained) audit log: wanted, but LATER, as its
      own task in the Audit domain. Not part of this module.
  D5. No `under_review` status for now. Concurrent admin review is rare at
      this stage; it can be added later.
  D6. Document files: pdf, jpg, jpeg, png — max 10 MB each.
  D7. Document storage: local disk now, behind DocumentStorageInterface
      (swap to S3 later without touching anything else).
      IMPORTANT: the PRIVATE `local` disk — NOT `public` like avatars.
      CNIC and bank scans must never be reachable by a public URL. Admins
      get them only through an admin-only download endpoint.
  D8. business_type is an enum: sole_proprietor, partnership, company.
  D9. Every state change is audited (same pattern as every other domain:
      Audit listener -> WriteAuditLogJob). See section 6.
  D10. Admin routes: auth:sanctum + active + role:super_admin|platform_admin
       (NOT "|admin" — that role never existed; the same bug was already
       fixed across the User domain). Every route group gets `active`.
  D11. All module exceptions extend App\Exceptions\DomainException and are
       mapped in bootstrap/app.php IN THE SAME STEP they are created, so the
       "exception exists but returns a raw 500" gap (Address, Auth) can't
       happen a third time.

Corrections found while re-reading v1:
  C1. v1 notified admins the moment the application row was created — but
      at that moment it has ZERO documents, so the admin opens an empty
      application. Fix: new `draft` status.
         create (draft) -> upload 5 docs -> Submit (draft -> pending)
         -> admins notified.
      Submit refuses if any document is missing — this is exactly what
      v1's MissingRequiredDocumentsException was meant for.
  C2. Documents can be uploaded/replaced ONLY while the application is
      draft or rejected. Otherwise a user could swap their CNIC after an
      admin approved it.
  C3. v1 assigned the 'seller' role twice (inside the approve action AND in
      UpgradeUserRoleOnApprovalListener). Now it happens ONCE, inside
      ApproveSellerApplicationAction, in the same DB transaction as the
      status change and the seller_profiles insert — so "approved but no
      seller role" can never happen. That listener is removed; listeners
      are only for side-effects (emails, audit).
  C4. The 'customer' role is KEPT on approval (assignRole adds, it does not
      replace) — a seller can still shop.
  C5. Customer routes have NO {id}. A user can only ever have ONE
      application (UNIQUE user_id), so every customer route resolves the
      application from $request->user() — same idea as routes/user/
      profile.php. No IDOR surface, so no SellerApplicationPolicy is
      needed. Admin access is enforced by route middleware, like Audit and
      Moderation.
  C6. store_name, business_name, business_type are what the admin verified,
      so they are LOCKED after approval. The seller profile can only edit:
      logo, description, business address, bank details.
  C7. Changing bank details is the classic payout-fraud move (hijack the
      account -> change the bank -> steal payouts). So a bank change is
      audited at WARNING severity AND the seller gets an email
      "your payout bank account was changed" (same idea as
      PasswordChangedNotification).
  C8. Re-uploading a document deletes the old file from storage (same as
      avatar replacement) — no orphaned CNIC scans left on disk.
  C9. `status` columns are plain strings and the value is always set in
      CODE, never left to a DB default (lesson from users.status + SQLite).
  C10. v1's `uploaded_at` column dropped — `updated_at` already records the
       last (re-)upload time.
  C11. Reaching the seller panel after approval. EnsurePanelAccess checks
       the `panel.seller.access` PERMISSION (which the seller role brings),
       not which login endpoint issued the token. So after approval:
         - login responses return accessible_panels: ["customer","seller"]
         - the frontend shows "Switch to Seller Dashboard" and keeps using
           the SAME token — no second login (Amazon-style)
       This is the main path on purpose: a customer who signed up with
       Google has a random password and could never use the password-based
       /v1/seller/auth/login. That endpoint still works for everyone else.
       Seller self-registration stays disabled (SellerAuthController
       already returns null from selfRegistrationRole()).

Added while building Phase 3:
  C12. An admin can never review their OWN application (segregation of
       duties) -> CannotReviewOwnApplicationException (403). Matters here
       because the super admin is also a normal customer account.
  C13. Approve/reject re-read the application row with lockForUpdate()
       inside the transaction. Two admins clicking at the same moment:
       the second waits, then sees the new status and gets a 409 — no
       double review, no second seller_profiles row.
  C14. Admin document download name is generated by us
       ("application-12-cnic_front.pdf"), never the customer's original
       file name — nothing user-controlled goes into the
       Content-Disposition header. A DB row whose file is missing from
       disk returns a clean 404, not a 500.
  C15. Approved/Rejected events fire AFTER the transaction commits, so an
       email is never sent for an approval that was rolled back.

Added while building Phase 4:
  C16. The store `description` and the logo go through the SAME blocking AI
       moderation as the user profile bio/avatar (EnforceContentModeration-
       Action) — they are shown publicly on the storefront.
       business_address is deliberately NOT moderated: the moderation
       prompt flags "exposed contact info", which a public store address
       always is (false positive every time).
  C17. The logo has its own endpoints (POST/DELETE /v1/seller/profile/logo)
       instead of riding on PUT /v1/seller/profile — PHP does not parse
       multipart/form-data bodies on PUT, so a file sent that way arrives
       empty. Same shape as the user avatar endpoints. Logos use a PUBLIC
       disk behind LogoStorageInterface (unlike KYC documents).
  C18. Pre-existing gap fixed: ModerationCheckFailedException (Gemini down
       or GEMINI_API_KEY missing) was never mapped, so profile/avatar
       updates crashed with a raw 500. Now 503 with a generic message; the
       real reason is only logged.
  C19. Bank fields are all-or-nothing (title + bank name + number together)
       and the number is normalised before validation (spaces/dashes
       removed, upper-cased), so the same IBAN typed two ways is not a
       "change". Accepted: Pakistani IBAN (PK + 2 digits + 4 letters +
       16 digits) or 8–24 digits. Adding the FIRST account = NOTICE audit;
       REPLACING one = WARNING audit. Both email the seller.
  C20. Seller profile routes also carry `panel:seller`, so they depend on
       exactly the permission the seller dashboard uses (C11).

1. STATUS LIFECYCLE (seller_applications.status)
--------------------------------------------------------------------------------

             edit info / upload / replace docs
                        ┌──────┐
                        ▼      │
      create ───►   [ draft ] ─┘
                        │
                        │ submit  (all 5 docs required)
                        ▼
                   [ pending ] ◄──────────────────────┐
                    │        │                        │
            approve │        │ reject (reason         │ resubmit
                    │        │  required)             │ (all 5 docs required,
                    ▼        ▼                        │  reason is cleared)
            [ approved ]  [ rejected ] ───────────────┘
              (final)       ▲      │
                            └──────┘
                 edit info / upload / replace docs

  What is allowed in each status:
    draft    : customer edits info, uploads docs, submits
    pending  : customer can only view; admin approves or rejects
    rejected : customer edits info, re-uploads docs, resubmits
    approved : application is frozen; seller now manages seller_profile

  Anything else -> InvalidApplicationStatusTransitionException (409).

4. DATABASE TABLES
--------------------------------------------------------------------------------

seller_applications
  id
  user_id                FK users, cascadeOnDelete           UNIQUE
  store_name             string(100)                         UNIQUE
  business_name          string(150)
  business_type          string(30)    BusinessType enum
  status                 string(20)    draft|pending|approved|rejected
                                       (always set in code — C9)
  rejection_reason       text, nullable   (cleared on resubmit)
  submitted_at           timestamp, nullable  (last time it went to pending)
  reviewed_by            FK users, nullable, nullOnDelete
  reviewed_at            timestamp, nullable
  timestamps
  INDEX(status)          -- the admin list filters by status

seller_application_documents
  id
  seller_application_id  FK seller_applications, cascadeOnDelete
  document_type          string(30)    SellerDocumentType enum
  file_path              string        path on the PRIVATE disk
  original_name          string        used as the admin download filename
  mime_type              string(100)
  size_bytes             unsigned integer
  timestamps             (updated_at = last re-upload — C10)
  UNIQUE(seller_application_id, document_type)   -- re-upload replaces

seller_profiles          -- created ONLY on approval: this is the LIVE business
  id
  user_id                FK users, cascadeOnDelete           UNIQUE
  seller_application_id  FK seller_applications              UNIQUE
  store_name             string(100)   UNIQUE  ┐ copied from the application,
  business_name          string(150)           │ LOCKED after approval (C6)
  business_type          string(30)            ┘
  logo_path              string, nullable   (PUBLIC disk — logos are public)
  description            text, nullable
  business_address       string, nullable
  bank_account_title     string, nullable
  bank_name              string, nullable
  bank_account_number    TEXT, nullable     `encrypted` cast + in $hidden (D3)
  bank_account_last4     string(4), nullable   display only
  status                 string(20)    active|suspended (set in code)
  timestamps

  Notes on the encrypted bank_account_number column:
  - It is encrypted with APP_KEY. If APP_KEY ever changes without being
    listed in APP_PREVIOUS_KEYS, every stored bank number becomes
    unreadable. Back up APP_KEY.
  - Encrypted values can't be searched, filtered or indexed in SQL. That's
    fine — we never look anything up by bank number.
  - Column type is TEXT because the ciphertext is much longer than the
    original number.
  - It is ALSO in the model's $hidden, so even an accidental toArray() /
    JSON dump can't leak it. Resources only expose "****" + last4.

10. PHASE 5 — AI DOCUMENT VERIFICATION  (DESIGNED, DEFERRED — decided 2026-09-24)
--------------------------------------------------------------------------------

  STATUS: BUILT (2026-09-24) — behind a switch that is OFF by default:
            SELLER_AI_VERIFICATION_ENABLED=false   (config/services.php)
          OFF -> NullDocumentVerifier: nothing is sent anywhere, every
                 document is "skipped", risk = unknown, admin reviews by eye.
          ON  -> GeminiDocumentVerifier. Turn ON only after Gemini billing
                 (PAID tier) is enabled. Optional GEMINI_VERIFICATION_MODEL.
  Also added: applicants must accept `accept_document_processing: true`
  when starting an application (consent, stored as
  document_processing_consent_at).
  Tests: SellerDocumentVerificationTest, GeminiDocumentVerifierTest,
  Unit/Seller/NameMatcherTest — all with fakes, no real AI calls.

  WHY IT IS BLOCKED (hard requirement, not optional):
    Gemini API terms for the FREE tier: "Do not submit sensitive,
    confidential, or personal information to the Unpaid Services." Free-tier
    prompts/files are used to improve Google products and human reviewers
    may read them. CNIC scans and bank statements must therefore ONLY ever
    go to the PAID tier (billing enabled), where Google states it does not
    use prompts or files to improve its products.
    Rough cost estimate at build time (verify pricing again before building):
    ~1–2 US cents per full application (5 documents).

  WHAT AI CAN / CANNOT DO (keep this honest in the UI and docs):
    CAN   : tell a CNIC from a selfie / random / explicit image; detect
            blurry, cropped or unreadable scans; read name, CNIC number,
            expiry, bank account title + last 4 digits, business name / NTN;
            point out *possible* signs of editing.
    CANNOT: prove a CNIC was genuinely issued by NADRA. A good forgery can
            pass. Real identity verification = NADRA Verisys API (paid,
            needs business registration) — separate, later.
    => AI assists; it NEVER approves. The admin's decision stays final.

  DECISIONS ALREADY TAKEN
    P5-1  Blocking power (answered: "hard errors block, the rest is flagged"):
          BLOCK at upload  : explicit/irrelevant image, wrong document type
                             (e.g. selfie as cnic_front), unreadable scan.
                             File is never stored; customer gets a clear
                             message ("This does not look like the FRONT of
                             a CNIC", "Photo is blurry — retake it").
          BLOCK at submit  : CNIC front/back numbers differ, CNIC expired.
          FLAG for admin   : name mismatches (e.g. "Muhammad" vs "M."),
                             possible tampering, bank title vs applicant/
                             business name mismatch, old bank statement.
    P5-2  Payout bank vs verified bank statement (answered: "allow + flag"):
          When the seller sets/changes payout bank details (Phase 4), compare
          last4 + account title with the values AI read from the APPROVED
          application's bank_statement. Mismatch -> save anyway, but WARNING
          audit + notify admins + mark the profile "bank_unverified" so the
          future Payouts domain holds payouts until an admin re-verifies.

  DESIGN (3 layers)
    Layer 1 — upload time, synchronous, per document
      DocumentVerifierInterface (swappable: GeminiDocumentVerifier now;
      NADRA / a self-hosted model later — fits the Python/ML learning track)
        verify(type, bytes, mime) -> verdict (ok | block) + reason
                                     + extracted fields + tamper notes
      PDFs and images both supported (Gemini accepts application/pdf inline).
      Only non-sensitive extracts are stored: CNIC number is needed for the
      front/back check; bank account -> last4 + title + bank name ONLY
      (never the full number).
      Provider down -> 503 (same as ModerationCheckFailedException, C18).
    Layer 2 — submit time, NO extra AI call
      Plain PHP compares the fields already extracted in Layer 1:
      front/back CNIC numbers equal, expiry > today, fuzzy name match
      (normalised: lowercase, strip "muhammad/m./syed", etc.), business name
      on license/tax vs application, statement title vs applicant/business,
      statement date within ~3 months. Deterministic = testable + reliable.
    Layer 3 — admin
      Application detail gains an ai_report: per-document verdict + extracted
      fields, every cross-check as pass/warn/fail with a reason, overall
      risk low/medium/high. Admin list can be filtered/sorted by risk.

  EXPECTED NEW PIECES (estimate — confirm when building)
    migrations : seller_application_documents + ai_status, ai_findings (json),
                 ai_checked_at; seller_applications + ai_risk_level,
                 ai_report (json), ai_checked_at; seller_profiles +
                 bank_verification_status
    code       : DocumentVerifierInterface, GeminiDocumentVerifier,
                 SellerDocumentVerificationService (Layer 2),
                 DocumentRejectedByAiException (422),
                 DocumentVerificationUnavailableException (503)
    audit      : SELLER_DOCUMENT_REJECTED_BY_AI, SELLER_BANK_UNVERIFIED
    consent    : applicant accepts "documents are checked by an automated AI
                 service" before first upload (discuss wording with a
                 lawyer before launch)
    tests      : all with a FakeDocumentVerifier — no real AI calls in CI

  TO SWITCH IT ON: enable Gemini billing, re-check pricing + terms, set
  SELLER_AI_VERIFICATION_ENABLED=true, `php artisan config:clear`, restart
  `queue:work`, then test with real sample documents before launch.

  SECURITY NOTES BAKED INTO THE BUILD
    - Prompt injection: text inside a document is DATA. Decisions come from
      strict booleans (anything but `false` for "explicit" = explicit;
      anything but `true` for "right document" = wrong document), fields are
      whitelisted + sanitised, and customer messages are OUR fixed text
      (DocumentRejectionCategory), never model-written.
    - The bank account is cut to its last 4 digits inside the verifier, even
      if the model returns the full number.
    - ai_findings (CNIC number, names, dates) is ENCRYPTED at rest
      (encrypted:array) and hidden from toArray(); only admin routes show it.
    - Provider errors log status only (never the body), users get a generic
      503 (DocumentVerificationUnavailableException).
    - FAIL messages (shown to the customer) never contain names/numbers;
      WARN messages (admin only) may.
    - Upload order: status check -> AI -> store. A locked application never
      costs an AI call; a rejected file never touches disk.

11. PHASE 6 — ADMIN CONTROL OF LIVE SELLERS + BANK MISMATCH EXIT

  Tests  : tests/Feature/Seller/AdminSellerControlTest.php

  WHY: two dead ends existed after Phase 5 —
    (a) once approved, admins could not even LIST live sellers, let alone
        stop a fraudulent one;
    (b) a payout bank marked "mismatch" had no way out.

  DECISIONS
    P6-1  Suspension closes the STORE, not the account (answered):
          - seller_profiles.status -> suspended (+ reason, who, when)
          - the seller can still OPEN the seller panel and read their

          - closing the whole account = the existing User-domain suspend
          - future Catalog/Orders: a suspended store's products are hidden
            and payouts stop
    P6-2  Leaving "mismatch" needs PROOF inside the system (answered):
          - the seller uploads a bank statement for the NEW payout account
            (private disk, same Layer 1 AI check as onboarding documents)

            -> "matched" automatically
          - otherwise (AI off, or AI read something different)
            -> "pending_review" + every seller reviewer is emailed
          - admin reviews: verify -> "admin_verified"; reject (reason
            required) -> back to "mismatch" + seller emailed with reason
          - ANY later bank change clears the proof and starts over
          - payouts (future Payment domain) only to a bank that is
            "matched" or "admin_verified" — SellerProfile::isPayoutBankVerified()

  BANK STATUS AFTER PHASE 6
      matched ─────────────────────────────── payouts allowed
      admin_verified ──────────────────────── payouts allowed
      unknown ─┐
      mismatch ┴─ seller uploads statement ─┬─ AI match ──► matched

      pending_review ─ admin verify ─► admin_verified

12. PHASE 7 — SELLER TEAM (owner / manager / staff)   (BUILT 2026-09-24)
--------------------------------------------------------------------------------

  Postman: postman/Seller_Phase7_Team.postman_collection.json
  Tests  : tests/Feature/Seller/SellerTeamTest.php


  WHY: a store is currently ONE user account. A growing store has to share
  the owner's password — staff could then change bank details, see payouts
  and delete things, and every audit row would say "the owner did it".

  THE ROLES ALREADY EXIST (RolePermissionMap, unchanged):
    seller          owner   — everything, incl. payments.payouts
    seller_manager          — same MINUS payments.payouts (runs the shop,
                              never touches the money)
    seller_staff            — view/create/update products + media, VIEW
                              orders and stock. No delete, no store
                              settings, no payouts.

  THE REAL PROBLEM: Spatie roles are GLOBAL. assignRole('seller_staff')
  says "this person is staff" but never "staff OF WHICH STORE". Today the
  question is answered by seller_profiles.user_id (UNIQUE = the OWNER), so
  findForUser($staffId) returns null and every seller endpoint 404s for a
  staff member. Hence a membership table — that is the actual work.

  DECISIONS
    P7-1  One person belongs to ONE store at a time (answered). Enforced in
          code (an active/invited membership anywhere blocks a new invite);
          the DB keeps unique(seller_profile_id, user_id) so re-inviting
          someone to the SAME store reuses their row instead of failing.
    P7-2  Only EXISTING accounts can be invited (answered). No email match
          -> 422 telling the owner to have them sign up first. No
          invitation tokens, expiry or signup-link machinery.
    P7-3  Only the OWNER manages the team (answered) — invite, change role,
          remove. A manager runs the shop but cannot bring in more people.

  C21. The accept/decline endpoints CANNOT sit behind role:seller — an
       invitee has no seller role yet, so that group would 403 them
       forever. They live in their own group: auth:sanctum + active only.
  C22. The owner gets a team row too, so "which store is this user in" has
       exactly ONE code path. The migration backfills an owner row for
       every existing seller_profile, and approval creates one from then on.
  C23. The owner can never change their own role or remove themselves —
       that would leave the store ownerless (403).
  C24. A suspended store (P6-1) blocks team changes too, not just profile
       edits.
  C25. Permission and suspension are checked BEFORE moderation, not after.
       Moderation is a billable network call; refusing a suspended store or
       a staff member afterwards means paying to reject them. The guards
       live in SellerProfileService::guardUpdate() and guardLogoChange(),
       which the action calls first and the service method calls again, so
       the service stays safe on its own. BOTH moderated seller writes are
       covered: the profile text update AND the logo upload.
  C26. phpunit.xml pins GEMINI_API_KEY and SELLER_AI_VERIFICATION_ENABLED so
       the suite never inherits .env. A real key in .env made tests call
       Google for real (billable, non-deterministic, HTTP 400 on fake
       uploads). tests/TestCase.php also calls Http::preventStrayRequests(),
       so any unfaked call now names its own URL instead of leaking out.

  ENDPOINTS
    Seller team (auth:sanctum, active, role:seller|seller_manager|seller_staff,
                 panel:seller)
      GET    /v1/seller/team                  list members (any member)
      POST   /v1/seller/team                  invite { email, role }   owner
      PATCH  /v1/seller/team/{member}         change role { role }     owner
      DELETE /v1/seller/team/{member}         remove                   owner
    Invitations (auth:sanctum, active ONLY — C21)
      GET    /v1/seller/invitations           my pending invitations
      POST   /v1/seller/invitations/{member}/accept
      POST   /v1/seller/invitations/{member}/decline

  WHO CAN DO WHAT (SellerTeamRole helpers, one place)
      owner    manage team, bank details, store profile, logo
      manager  store profile, logo            (no team, no bank)
      staff    read only on the store profile (products come with Catalog)

  GUARDS
    invite yourself -> 422 | role=owner -> 422 (validation in:manager,staff)
    email has no account -> 422 (P7-2)
    already in a store -> 409 (P7-1)
    owner touching their own membership -> 403 (C23)
    manager/staff managing the team -> 403 (P7-3)
    accepting someone else's invitation -> 404
    accepting an already-accepted/revoked one -> 409
    suspended store -> 403 (C24)

  AUDIT (category SELLER_MANAGEMENT)
    SELLER_TEAM_MEMBER_INVITED INFO, SELLER_TEAM_MEMBER_JOINED NOTICE,
    SELLER_TEAM_ROLE_CHANGED NOTICE, SELLER_TEAM_MEMBER_REMOVED NOTICE
    Every row records WHICH member acted — the whole point of the feature.

13. PHASE 8 — CLOSING THE SELLER DOMAIN            (BUILT 2026-09-24)
--------------------------------------------------------------------------------
  Three gaps stand between "the flow works" and "we never have to come back
  to this domain": documents that expire after approval, a seller with no way
  out, and an unmetered paid AI call. Plus one leftover from P7.

  ------------------------------------------------------------------
  13a. DOCUMENT EXPIRY AND RE-KYC                       (BUILT)
  ------------------------------------------------------------------
  Postman: postman/Seller_Phase8_Renewals.postman_collection.json
  Tests  : SellerDocumentRenewalTest, SellerKycExpiryTest
  THE BLOCKER: what the AI read is stored `encrypted:array`
  (seller_application_documents.ai_findings). Ciphertext cannot be queried,
  so `where date_of_expiry < now()` is impossible. A scheduled job can never
  find an expiring seller through that column. This is the price we already
  chose to pay for encryption-at-rest, and it has to be paid here.

  DECISIONS
    P8-1  At APPROVAL, copy only the DATES out of the encrypted findings
          into plain, indexed columns on seller_profiles:
            cnic_expires_at     <- cnic_front.date_of_expiry
            licence_expires_at  <- business_license.expiry_date
          A date is not the secret; the CNIC NUMBER is, and that stays
          encrypted. Query on the date, never on the identity.
    P8-2  Expiry does NOT close the store (answered). 30 days out the seller
          is warned; at expiry the store keeps selling but PAYOUT STOPS until
          a fresh document is approved. Earning is allowed, withdrawing is
          not — the money is safe either way, and a seller on holiday does
          not lose their business over an email they missed.
    P8-3  Payout readiness is TWO independent facts, so it gets TWO columns.
          bank_verification_status answers "is this bank account proven to be
          theirs"; the NEW kyc_status answers "is their identity still
          valid". Overloading the first with the second would lose the bank
          status on expiry and make re-KYC have to guess what to restore.
            SellerKycStatus: valid | expiring_soon | expired
            SellerProfile::isPayoutReady()
                = bank_verification_status->isPayoutReady()
               && kyc_status !== EXPIRED
    P8-4  Re-uploaded documents go AI-first, then admin confirms (answered) —
          the same two-layer shape as onboarding, because re-KYC is exactly
          where someone would paste another person's document.

  C27. A NULL expiry date is NOT an expiry. AI verification is off by
       default, so most sellers have no date at all. The job must treat
       NULL as "nothing known" and leave them VALID — otherwise the day AI
       is switched on, every existing seller flips to EXPIRED at once.
  C28. The renewal does NOT touch seller_application_documents. The
       application is the frozen record of what the admin actually approved;
       rewriting it would destroy the audit trail. Renewals live in their
       own table and the approved date is copied onto seller_profiles.
  C29. The daily job notifies on a STATE CHANGE, not on a condition. Without
       kyc_notified_at it would email the same seller every morning for 30
       days straight.

  NEW TABLE  seller_document_renewals
    seller_profile_id, document_type, file_path (private disk),
    original_name, mime_type, size_bytes,
    ai_status, ai_findings (encrypted), ai_checked_at, extracted_expiry_date,
    status (pending|approved|rejected), reviewed_by, reviewed_at,
    rejection_reason, timestamps
    index(status), index(seller_profile_id)

  NEW COLUMNS  seller_profiles
    cnic_expires_at (date, null, index)
    licence_expires_at (date, null, index)
    kyc_status (string 20, index, default 'valid')
    kyc_notified_at (timestamp, null)     -- C29

  SCHEDULED  seller:check-document-expiry   daily
    NULL dates skipped (C27). Within 30 days -> expiring_soon + one email.
    Past  -> expired + one email + payouts stop. A fresh approval resets
    both the date and the status, and clears kyc_notified_at.

  ENDPOINTS
    Seller   POST /v1/seller/documents          re-upload { document_type, file }
             GET  /v1/seller/documents          my renewals + their status
    Admin    GET  /v1/admin/seller-renewals     pending queue (oldest first)
             GET  /v1/admin/seller-renewals/{id}/file    download
             POST /v1/admin/seller-renewals/{id}/review  { decision, reason? }

  ------------------------------------------------------------------
  13b. SELLER CLOSES THEIR OWN STORE                    (BUILT)
  ------------------------------------------------------------------
  Postman: postman/Seller_Phase8b_Closure.postman_collection.json
  Tests  : SellerStoreClosureTest
  DECISIONS
    P8-5  `closed` is a THIRD status, never reusing `suspended`. Suspended
          means the platform punished them; closed means they walked away.
          Conflating the two would make the audit trail lie about which
          happened, and those two facts are not legally interchangeable.
    P8-6  Reopening needs ADMIN approval (answered). The seller asks, the
          admin checks the bank and documents are still good, then reopens.
          No new application, no re-uploading everything — but also no
          closing to duck a review and quietly reopening later.

  C30. A SUSPENDED store cannot be closed by its seller. Otherwise closing
       becomes the escape hatch from an investigation.
  C31. The team rows are KEPT on closure, only the Spatie roles come off
       (every member, owner included). Reopening restores the roles from
       those rows — the team does not have to be rebuilt by hand.
  C32. Nothing is ever deleted. Orders and audit history hang off this
       record; the row outlives the business.
  C33. `ensureNotSuspended` becomes `ensureStoreOpen` and refuses BOTH
       suspended and closed. Every existing write guard picks this up for
       free — miss one and a closed store is still editable.
  C34. Closing asks the seller to type their store name back. A one-click
       button that dissolves a business is a bug, not a feature.

  NEW COLUMNS  seller_profiles
    closed_at (timestamp, null), closure_reason (text, null),
    reopen_requested_at (timestamp, null)

  ENDPOINTS
    Seller   POST /v1/seller/profile/close    { confirm_store_name, reason? }
             POST /v1/seller/profile/reopen   ask the admin to reopen
    Admin    POST /v1/admin/sellers/{seller}/reopen   approve the request

  C39. The OWNER keeps their `seller` role when the store closes; only the
       other members lose theirs. Stripping the owner's too would lock them
       out of every seller route — including the one that ASKS for the store
       back, which is their only way out. This mirrors suspension (P6-1):
       the panel still opens, it just refuses every write.
  C40. Closure exposed a latent bug in Phase 6. suspend() tested
       `status === SUSPENDED` and reactivate() tested `status === ACTIVE` —
       correct while those were the only two states. With CLOSED added,
       reactivate() would have accepted a CLOSED store and flipped it to
       active through the WRONG door: closed_at left behind and the team's
       roles never restored. Both now name the state they require
       (`isOpen()` / `=== SUSPENDED`) instead of the one they reject.
       Lesson: a `!==` guard silently widens every time a new enum case is
       added; name what you ALLOW, not what you forbid.

  ------------------------------------------------------------------
  13c. RATE LIMITING THE PAID AI CALLS                  (BUILT)
  ------------------------------------------------------------------
  C35. Every document upload is a BILLABLE AI call made BEFORE the file is
       stored — so a REJECTED upload costs money too. Without a limit one
       loop runs up our bill. `throttle` sits on the route, ahead of the
       controller, so a throttled request never reaches the AI at all.
       Per authenticated USER, not per IP: they are all logged in, and an
       IP limit would punish everyone behind one office connection.
       Limits: documents 20/hour, bank proof 5/hour, renewals 10/hour.

  ------------------------------------------------------------------
  13d. LEFTOVER FROM PHASE 7                            (BUILT)
  ------------------------------------------------------------------
  C36. P7-1 (one person, one store) was only enforced at INVITE time, so a
       staff member could still start their own application and only hit the
       wall at approval — after doing all the work and paying for the AI
       checks. The check moves to application creation, where the answer is
       already knowable.

  C37. SellerProfileFactory creates an application for every store it makes
       (that is how a store exists at all), so a test asserting "this user
       got no application" must scope to THAT USER, never count the whole
       table. assertDatabaseCount(0) there was asserting nothing true.
  C38. Two mistakes worth not repeating, both caught only at runtime:
       PHPUnit's TestCase::run() is FINAL — a test helper named run()
       makes the whole class a fatal error; and Illuminate\Support has
       Carbon but NOT CarbonImmutable in this framework version. The house
       style is Carbon\CarbonInterface for hints, Carbon\CarbonImmutable
       for now(). `php -l` catches neither — it only reads syntax.

  TESTS TO ADD
    expiry job: null dates untouched | 30-day warn once, not daily |
      expiry stops payout but keeps the store open | approval resets it
    renewals: ai rejects before storing | admin approves -> new date +
      kyc valid | admin rejects -> reason + retry allowed
    closure: suspended cannot close (C30) | wrong store name refused (C34) |
      roles come off, team rows stay (C31) | closed store refuses writes
      (C33) | admin reopen restores roles
    throttle: 21st upload in an hour -> 429 and NO ai call
    C36: a team member cannot start an application

14. PHASE 9 — THE LAST OF THE SELLER DOMAIN        (BUILT 2026-09-24)
--------------------------------------------------------------------------------
  What is left after Phase 8, minus the things that belong to other domains
  (payouts need Orders/Payments; the public store page comes with Catalog).

  ------------------------------------------------------------------
  14a. KYC DOCUMENT RETENTION                           (BUILT)
  ------------------------------------------------------------------
  Postman: postman/Seller_Phase9_Retention_Rename.postman_collection.json
  Tests  : SellerKycRetentionTest
  THE GAP: we collect CNIC scans and bank statements and NEVER delete them.
  A seller rejected five times leaves five copies of their identity document
  on disk forever. Closure (13b) is what finally makes this fixable: until
  there was a way for a relationship to END, there was no clock to start.

  DECISIONS
    P9-1  Two different clocks, because the files answer two different
          questions:
            SUPERSEDED evidence — a rejected renewal, or an approved one
            that a newer approved renewal has replaced. It proves nothing
            current. Keep the FILE 90 days (long enough to settle a
            dispute), then purge it.
            CURRENT evidence — the onboarding documents and the newest
            approved renewal per type. These are what the admin approved,
            so they live as long as the business does, plus a retention
            period after it ENDS (closed, per 13b).
    P9-2  The ROW is never deleted, only the file. The row keeps saying a
          document existed, who reviewed it and when — and now also
          file_purged_at. Deleting the row would erase the KYC history we
          are legally required to be able to show.
    P9-3  The retention window is CONFIG, not a literal buried in code:
            config('seller.kyc_retention_days')       default 1825 (5 yrs)
            config('seller.superseded_retention_days') default 90
          1825 days is the common AML/KYC figure, NOT legal advice and NOT
          verified for Pakistan. Confirm it with a lawyer before launch;
          changing it is one .env value, by design.

  C41. Purging is driven by CLOSED_AT, never by "inactive for a while". A
       quiet seller is still a seller; only a store that actually ended
       starts the clock.
  C42. A suspended store's documents are NEVER purged, whatever the dates.
       Suspension usually means an investigation is open, and destroying
       the evidence mid-investigation is the worst possible time to do it.
  C43. The purge is idempotent and file-first: delete the file, then stamp
       file_purged_at. If it dies in between, the next run simply finds a
       missing file and stamps it — never the reverse, which would leave a
       file on disk that nothing points at any more.

  NEW COLUMNS
    seller_application_documents : file_purged_at (timestamp, null)
    seller_document_renewals     : file_purged_at (timestamp, null)

  SCHEDULED  seller:purge-expired-kyc-documents   daily
    superseded/rejected renewals older than superseded_retention_days
    + every document of a store closed longer ago than kyc_retention_days

  14b. CHANGING THE STORE NAME AFTER APPROVAL           (BUILT)
  ------------------------------------------------------------------
  Postman: postman/Seller_Phase9_Retention_Rename.postman_collection.json
  Tests  : SellerStoreRenameTest
  THE GAP: C6 locked store_name forever at approval. That was right — the
  admin verified it — but "forever" is wrong: real businesses rebrand, and
  today the only route is to close and start over.

  DECISIONS
    P9-4  The seller REQUESTS, an admin approves. Same shape as everything
          else the admin verified. No new table for one field: two columns
          on seller_profiles (pending_store_name, store_name_requested_at)
          carry the whole thing.
    P9-5  Owner only. A manager runs the shop; the shop's NAME is the
          business's identity, which is the owner's.

  C44. Uniqueness is checked TWICE — when the name is requested AND again
       inside the approval transaction. Between the two, another store can
       take that name. Checking only at request time is the classic race
       that ends with two stores sharing a name and a UNIQUE index blowing
       up in an admin's face.
  C45. The old name stays live until the moment it is approved. A request
       is not a rename; nothing user-visible changes while it is pending.
  C46. The admin list validated `in:active,suspended`, typed out by hand.
       CLOSED was added to the enum in 13b and that list did not follow, so
       closed stores were silently unfilterable. The rule now derives from
       SellerProfileStatus::values(). Same family as C40: a hand-written
       copy of an enum rots the moment the enum grows.
  C47. Query ordering goes LAST and the cases are exclusive. Chaining
       reorder() for the rename queue and then latest('id') produced BOTH
       orderings — the queue was sorted by request date, then re-sorted by
       id. A queue is oldest-first (nobody waits behind a later arrival);
       a browse list is newest-first.

  NEW COLUMNS  seller_profiles
    pending_store_name (string 100, null)
    store_name_requested_at (timestamp, null)

  ENDPOINTS
    Seller   POST /v1/seller/profile/name          { store_name }
             DELETE /v1/seller/profile/name        withdraw the request
    Admin    GET  /v1/admin/sellers?name_pending=1 who is waiting
             POST /v1/admin/sellers/{id}/name/review { decision, reason? }

  ------------------------------------------------------------------
  14c. `under_review` ON APPLICATIONS — DELIBERATELY NOT BUILT
  ------------------------------------------------------------------
  D5 deferred this and it stays deferred, now as a decision rather than a
  postponement.

  The danger it guards against — two admins reviewing the same application
  and one overwriting the other — is ALREADY handled: every review locks
  the row FOR UPDATE inside a transaction (C13), so the second admin waits,
  sees the new status, and gets a clean 409. Nothing can be corrupted.

  What `under_review` would add is only politeness: not wasting a second
  admin's reading time. The cost is a fourth status in the lifecycle, claim
  and release endpoints, stale-claim expiry (an admin who claims and goes
  home must not freeze an application forever), and every existing status
  check re-examined. That is a poor trade at one reviewer.

  BUILD IT WHEN: reviewers regularly collide — say a queue deep enough that
  two people work it at once. Not before.
